* Boot-edge findings

The privileged capture supplied for the current boot and the later unprivileged
runtime checks establish:

- TSC was again rejected for frequency skew and Linux switched to HPET.
- The TPM CRB ACPI resource mismatch and probe error =-16= remain; no
  =/dev/tpm*= device exists and =/sys/class/tpm= is empty.
- The AMD platform-security device is bound to =ccp=, but the boot log still
  reports that PSP access failed.  No SEV device is present.
- The exact early =init[1]= Guile address-boundary probe remains the previously
  attributed handled BDWGC probe.  Shepherd is healthy as PID 1.
- The former IRQ 7 =pinctrl_amd= storm is absent from both the filtered boot
  capture and the live interrupt table after more than one day of uptime.
- No hardware-error or machine-check event appeared in the filtered capture;
  the live interrupt table showed zero machine-check exceptions.

The IRQ result is one-boot evidence, not proof that firmware permanently fixed
the route.  TSC, TPM, and PSP remain platform/firmware findings; this refresh
does not select kernel parameters or local workarounds.

* Build-concurrency measurement

The CPU now exposes eight logical CPUs while Guix still permits one build job
with up to four reported cores.  A bounded comparison rebuilt the same upstream
Zstd 1.5.7 and SQLite 3.53.1 derivations with:

#+begin_example
guix build --check --no-substitutes --no-offload --no-grafts \
  --max-jobs=M --cores=C ZSTD_DRV SQLITE_DRV
#+end_example

Both outputs and their inputs were already present.  Each scored run therefore
rebuilt exactly those two independent derivations and checked reproducibility.

| Case | Jobs x cores | Wall time | Change from current | Peak builders | Peak temperature | Emacs RPC median / p95 / max |
|------+--------------+-----------+---------------------+---------------+------------------+------------------------------|
| Current | 1 x 4 | 144.14 s | baseline | 1 | 60.0 C | 7.14 / 8.73 / 9.30 ms |
| Wider job | 1 x 8 | 140.94 s | 2.2 percent faster | 1 | 65.4 C | 8.40 / 15.66 / 19.46 ms |
| Parallel jobs | 2 x 4 | 94.96 s | 34.1 percent faster | 2 | 63.9 C | 6.60 / 8.91 / 9.80 ms |

All three checks passed.  Swap remained unused, Emacs answered every probe, and
at least 24.7 GiB remained available.  The =2 x 4= run's sampled builder RSS
peaked at 1.46 GiB, compared with about 0.90 GiB for either one-job run.

The measured candidate is =--max-jobs=2 --cores=4=.  Giving one build eight
cores produced only a 2.2 percent change; allowing two four-core builds produced
a clear 34.1 percent reduction for this two-derivation workload.  This record
does not change or activate the daemon policy.

The initial custom =kitty-latest= candidate was excluded after its =--check=
rebuild differed from the existing output.  Pinned upstream Guix provides Kitty
0.46.2 while =sk-guix= provides 0.47.4; replacing the custom package with the
older upstream package is a separate package decision, not a concurrency test.
That separate source decision was accepted later on 2026-08-12: =sk-guix= is
preserved but removed from the active channel and build-gate policy.  No System
build, activation, or runtime acceptance is claimed by that decision.  The
accepted tradeoff is an older Kitty security baseline: 0.46.2 lacks later fixes
for CVE-2026-33633, CVE-2026-33642, CVE-2026-42850, CVE-2026-42851,
CVE-2026-54055, and CVE-2026-54057; CVE-2026-54056 affects the newer
drag-and-drop feature absent from 0.46.2.  Revisit when upstream Guix carries
equivalent fixes or reactivate =sk-guix= if the accepted risk becomes
unacceptable first.
