#+title: GuixPC configuration
#+startup: overview

* Overview

This repository is the human-edited source of truth for =guixpc=.  It defines
the Guix System, Guix Home environment, and Emacs/EXWM desktop used on the
machine every day.

The goal is a coherent, reliable, responsive, and maintainable workstation
built around Guix, EXWM, Guile Scheme, and Emacs Lisp.  It is not a language
collection, research project, or authorization to build infrastructure without
a practical benefit to the running system.

The supported target is the Lenovo ideacentre 510A-15ARR named =guixpc=.  Its
[[file:docs/audits/2026-08-12-hardware-baseline-refresh.org][current hardware baseline]] reflects the Ryzen 5 2400G and BIOS update; the
[[file:docs/audits/2026-07-12-full-configuration-audit.org][full configuration audit]] preserves the original configuration findings.

Current operating model:

- Guix System owns hardware, boot, filesystems, system services, and a small
  tty recovery floor.
- Guix Home owns the normal package set, Fish, Emacs, session D-Bus,
  PipeWire/WirePlumber, fonts, themes, and managed dotfile links.
- Emacs 31 runs EXWM as the desktop; tty1 remains the local recovery entry
  point.
- GTK 3/4, Emacs, Kitty, Fish, wallpaper, fonts, icons, and cursor share the
  accepted dark visual policy.  Qt normalization is not yet implemented.
- Channel inputs are authenticated and pinned.
- Generation retention is inspection-only.  No automatic System-generation
  deletion or store-garbage-collection job is approved.

* Safe first look

Run these non-activating checks from =~/Projects/guix-dotfiles= on =guixpc=:

#+begin_src sh
git status --short --branch
scripts/guix-entrypoints check
scripts/sk-status
ghr --print
gsr --print
#+end_src

They verify the declaration links, report current system state, and print the
Home and System reconfiguration plans.  =ghr= and =gsr= are Fish aliases.
These commands do not activate a configuration.

For daily use, activation, channel updates, recovery, and rollback, use the
[[file:docs/operator-manual.org][GuixPC operator manual]].

| Machine record               | =guix/machines/guixpc/=                    |
| Documentation                | =docs/=                                     |

The supported Guix entry points under =~/.config/guix= link into the channel,
Home, and System files above.  =scripts/guix-entrypoints check= verifies them
without changing them.  Bootstrap and repair procedures belong in the operator
manual.

The repository owns human-edited configuration.  Guix store outputs,
generations, caches, application history, and other generated state are not
source files and must not be edited as configuration.

* Project contract

** Work from explicit outcomes

Before implementation, define:

- the user objective and observable result;
- affected files and live surfaces;
- non-goals;
- the smallest relevant checks;
- build, activation, reboot, and hand-test requirements;
- rollback and stopping point.

Adjacent features, packages, languages, abstractions, and experiments remain
out of scope until explicitly accepted.  A =TODO=, =BACKLOG=, test, or existing
source file does not authorize work by itself.

If a slice expands materially, stops producing practical progress, or its
value is questioned, stop and reassess.  Report what changed, what reached the
live machine, what remains, and the realistic cost.  A scope or value concern
is not answered by arguing for more work.

** Use native Lisp for custom behavior

- Guile Scheme owns Guix declarations, services, system utilities, and
  standalone tools.
- Emacs Lisp owns Emacs and EXWM behavior.
- Shell is limited to small operating-system boundary glue; feature logic
  remains in Scheme or Emacs Lisp.

Existing upstream software may use other languages.  A new dialect or
non-Lisp implementation needs a concrete requirement and explicit approval.

** Prove the changed layer

Keep these claims separate:

1. source is valid;
2. a candidate builds;
3. a configuration was activated;
4. the expected runtime owns the new state;
5. any required hand test passed.

A build, test suite, document, or generated artifact is not a live system
improvement.  Claim completion only at the requested boundary.

** Stop at the accepted boundary

Use the smallest source change and focused validation that prove the requested
outcome.  Publish a signed, clean checkpoint before activation.  Build and
activate only the Guix layer that changed, then perform the required runtime
and human acceptance.

Stop and reassess when a second unexpected prerequisite appears, the promised
outcome changes, or more than one correction checkpoint is needed.  Tests and
evidence support a slice; they may not become a separate project.
